# Media Ops — engine recommendation and design changes

**Date / source retrieval:** 2026-09-04.  
**Status:** Documentation and prototype research complete; recommendation, not an approved implementation plan or a live feasibility result.  
**Scope:** Slice 1 only. No app code, workflow builds/deployments, authenticated provider calls, prototype credentials, or paid generations were used.  
**Supporting reports:** [Comfy API findings](2026-09-04-comfy-api-findings.md), [Krea and workflow fit](2026-09-04-engine-workflow-fit.md).  
**Baseline:** [Research brief](2026-09-04-krea-comfy-engine-brief.md), [design](../specs/2026-09-04-muse-media-ops-slice-1-design.md), [review](../specs/2026-09-04-muse-media-ops-slice-1-review.md).

## Recommendation

**Use Krea as the primary and only implemented image engine for slice 1, subject to validating the studio's actual workflow versions. Keep Comfy Developer Platform as a deferred secondary option selected per pipeline. Do not implement automatic fallback.** Confidence is **medium** in the engine choice and **high** in the recovery/storage boundaries below. Neither engine's actual studio workflow quality, latency, cost, or complete 4K delivery has been measured here.

Krea is the smaller initial integration because the supplied prototypes already specify its generator and editor payloads. Its version endpoint exposes input/output schemas, which fits the configurable Filament generator. This supports reusing an existing integration approach; it does not establish that the referenced node apps remain accessible or produce approved imagery. [Krea version metadata](https://www.krea.ai/docs/api-reference/node-apps/get-a-node-app-by-version-id), [local evidence](2026-09-04-engine-workflow-fit.md).

Comfy is a credible alternative when the studio wants to own model, node, and environment choices. The researched product is the **hosted Developer Platform**, using a deployment-specific `*.run.comfy.app` endpoint and HTTP API v2. Comfy Cloud subscriptions, self-hosted ComfyUI, and the separate Router are different choices. Laravel can call the documented HTTP interface directly; a Python or Node application service is unnecessary. Workflow authoring and release management still require a Comfy toolchain and a named maintainer. [Comfy API v2](https://docs.comfy.org/api-reference/v2/overview), [developer overview](https://docs.comfy.org/development/overview).

“Secondary” means an Art Director can eventually register a separately validated Comfy generator, editor, or upscaler and assign it to a campaign. Editors choose the configured generator label, or use the campaign's configured editing/delivery action. Engine details stay in administration. The engine is fixed for each accepted execution. A restart preserves its original engine and configuration; changing engines is a new configured operation with appropriate confirmation, not recovery. Supporting both providers does not require launching both in slice 1.

If Krea fails the workflow-access, image-transport, or exact-size gate, revisit the affected pipeline. Comfy could then supply that pipeline without moving all generators. Comfy-only should be reconsidered if ownership of the full inference stack becomes a release requirement and the studio accepts the porting and operating work.

## What the evidence establishes

**Verified** means stated in current primary documentation or visible in static prototype source, not experimentally verified. **Inferred** means our engineering assessment. **Unverified** means missing account/workflow evidence or a live measurement. **Unsupported** means a claim the inspected evidence does not justify.

| Question | Evidence and implication |
| --- | --- |
| Do both accept the same workflow? | **Unsupported.** Krea accepts values matching a node-app version schema. Comfy accepts a ComfyUI API graph. Its first v2 surface has no named workflow parameter/introspection system equivalent to Krea's form schema. Use an explicit studio field-to-node-input map. [Krea execute](https://www.krea.ai/docs/api-reference/node-apps/execute-a-node-app), [Comfy design notes](https://docs.comfy.org/development/api-development/sdks-design), [graph format](https://docs.comfy.org/development/api-development/workflow-api-format). |
| Are the prototype workflows portable? | **Verified locally:** Santander text input; Skechers three images; Invierno one image/four texts; editor source image/instruction. **Inferred:** these product forms are portable. The actual graphs, model versions, LoRAs, preprocessing, output multiplicity, and art-direction fidelity are **unverified**. No actual upscaler integration was found. See the [payload inventory and acceptance matrix](2026-09-04-engine-workflow-fit.md). |
| Does Comfy solve lost submission responses? | **No documented full solution.** Its specification rejects a reused idempotency key with `422 idempotency_key_reuse`, retains uncertain claims, and expires keys after 24 hours. It does not replay the original response. The official CLI reference confirms no job-list, lookup-by-key, or caller-assigned job ID for recovering that gap. [Canonical v2 contract](https://raw.githubusercontent.com/Comfy-Org/docs/main/openapi-v2.yaml), [official deployment reference](https://github.com/Comfy-Org/comfy-cli/blob/main/comfy_cli/skills/comfy-deploy/SKILL.md). |
| Does Krea job listing remove that gap? | **Unsupported.** Listing exists, but its documented filters are cursor, limit, types, and status, without client request correlation. Matching by time or prompt is insufficient to attach workspace-wide jobs to a brand. Known IDs can be polled. [List jobs](https://www.krea.ai/docs/api-reference/general/list-jobs), [get job](https://www.krea.ai/docs/api-reference/general/get-a-job-by-id). |
| Is a successful upscale automatically 4K? | **No.** Krea's Enhance scale factor and Topaz dimensions offer candidate controls, but exact output rounding and precedence need testing. Both engines must return `round(W × s) × round(H × s)`, `s = 3840 / max(W,H)`. Provider/model “4K” labels are insufficient. [Krea Enhance](https://www.krea.ai/docs/api-reference/image-enhance/krea-enhance), [Topaz](https://www.krea.ai/docs/api-reference/image-enhance/topaz). |

### Reconciled documentation conflicts

1. **Comfy “idempotent” overview versus detailed semantics:** the overview is compatible with duplicate prevention, not guaranteed job discovery or response replay. Retain an unknown-submission outcome. A reused key can also start work if the first request never arrived or its claim was released; replay is not a generally free recovery operation.
2. **Comfy “one pinned workflow” versus graph submission:** the specific deployment guide and CLI describe a release-pinned environment receiving API graphs. Store both graph revision and environment release. Do not invent a named-input endpoint or rely on a deployment-level `GET /workflow`. Confirm the chosen endpoint in the experiment. [Deployment guide](https://docs.comfy.org/development/serverless/overview), [deployment reference](https://github.com/Comfy-Org/comfy-cli/blob/main/comfy_cli/skills/comfy-deploy/SKILL.md).
3. **Krea compute-unit marketing versus API billing:** use the specialist billing documentation: bearer API calls debit a separate workspace USD balance; web-app compute units are different. Node-app total cost still requires its constituent jobs/configuration. [API billing](https://www.krea.ai/docs/developers/api-keys-and-billing), [API product page](https://www.krea.ai/features/api).
4. **Krea data URIs versus schema length:** Enhance documents data URIs while limiting the image string to 1,024 characters. This is a specific documentation conflict, not proof every node app rejects base64. The prototype's base64 approach is evidence of intended transport only. Validate actual schemas and large payloads; evaluate multipart assets or private signed input URLs where supported. [Enhance schema](https://www.krea.ai/docs/api-reference/image-enhance/krea-enhance), [asset upload](https://www.krea.ai/docs/api-reference/assets/upload-an-asset).

## Compare the three practical choices

The assessments below are **inferences** from the supporting reports. No latency, quality, or cost winner has been measured.

| Dimension | Krea only | Comfy only | Per-pipeline selection, both implemented |
| --- | --- | --- | --- |
| Functional coverage | Best reuse of supplied payloads; 4K still needs a configured/tested path | New generator/editor workflows and explicit bindings required | Choose each pipeline's validated implementation; doubles integration coverage |
| Art-direction continuity | Existing node-app versions are the best starting candidate; require approved examples | Recreate models, instructions, composition, references, preprocessing, and sizing | Separate acceptance for each binding; engine substitution can change results |
| Reproducibility | Pin node-app version and typed inputs; upstream model behavior remains a dependency | Pin graph, model digests, nodes, ComfyUI/environment release, and seeds where exposed | Preserve complete provider snapshot for every generation |
| Configuration | Remote schema plus Art Director overrides | Studio manifest plus field mapping, release, GPU/region, output-node choices | Common form contract; provider-specific registration and readiness |
| Latency | Queue/model time unmeasured | Adds cold-start/model-loading tradeoff when scaled to zero | No latency advantage established; no automatic race between providers |
| Cost | API USD per completed job; aggregate workflow cost unverified | Worker seconds, startup/idle tail, storage, build charges, possible partner calls | Both commercial/operating models; duplicated work is a possible extra charge |
| Recovery | Known job IDs and saved output manifests; unknown submission remains ambiguous | Durable known IDs/assets; duplicate prevention but same unknown-ID gap | Same conservative policy for both; no cross-engine recovery |
| Operations | Smaller initial burden; provider operates models/inference | Studio owns dependencies, releases, capacity choices, retirement, license review | Worth adding only for a concrete pipeline benefit |

A pinned graph/release improves traceability; it does not promise identical pixels across runs or provider/model changes. “Comfy is cheaper,” “Comfy is production-ready for these workflows,” and “Krea already covers 4K” remain **unsupported**.

### Costs to carry into planning

Current published Comfy Developer Platform GPU rates include RTX PRO 6000 at **$3.49/worker-hour**, H100 **$4.79**, H200 **$5.93**, and B200 **$8.64**, billed by second. Standard network storage below 1 TB is **$0.091/GB-month**; container disk is listed separately at **$0.13/GB-month**. These are inputs to an estimate, not per-image prices. [Published resource prices](https://comfy.org/pricing).

Minimum workers are billed while idle. Flex workers include startup/model loading and a current 30-second idle tail; zero minimum workers avoid idle compute. Pausing retains billed model storage; old releases/deployments need an explicit retirement policy. The official build reference also says release creation incurs build-minute charges, whose rate was not found in public pricing. Egress and any account-specific minimum need confirmation. [Serverless billing](https://docs.comfy.org/development/serverless/overview), [build reference](https://github.com/Comfy-Org/comfy-cli/blob/main/comfy_cli/skills/comfy-build/SKILL.md).

Use `Comfy cost = build minutes × confirmed build rate + Σ(worker seconds × GPU rate / 3600) + storage + partner calls + confirmed transfer charges`, plus applicable taxes. Confirm whether worker disk is included or additive: the serverless guide and pricing page describe its accounting differently. One hypothetical continuously warm RTX PRO 6000 worker for 30 days is **$2,512.80 GPU-only** (`3.49 × 24 × 30`); this is arithmetic illustrating a configuration choice, not recommended capacity or a quote. For Krea, sum the configured workflow's completed-job prices. Treat successfully completed work whose output fails our 4K validator as potentially billable; aggregate billing for a partially failed node app remains unverified.

## Smallest practical adapter boundary

This is a **proposed design**, not implementation. Keep one `ImageEngine` interface, one Krea adapter initially, and a provider registry selecting it from an immutable pipeline binding. No plugin framework, routing rules engine, common node graph, or deployment control plane in Media Ops.

| Operation | Contract and responsibility |
| --- | --- |
| `describe(binding) → PipelineContract` | Return native identity/revision, supported normalized fields, explicit input/output mappings, limits, and capability metadata. Krea maps its schema subset; future Comfy loads a versioned studio manifest. Activation validates the entire binding. |
| `prepare(snapshot, mediaRefs, priorPreparation) → PreparedSubmission` | Resolve authorized studio image references into provider transport. Return resumable staged-asset references and a secret-free prepared payload reference/hash. Persist preparation before the one-time submission claim. This step cannot execute a workflow. |
| `submit(prepared, attemptKey) → SubmissionOutcome` | One authorized generation attempt: return `accepted(handles[])`, `rejected(error)`, or `unknown(error)`. Retain every handle. No hidden HTTP/SDK submission retries. |
| `inspect(handle) → JobObservation` | Read current normalized and native status, progress, retention deadline when available, committed output references, and error. Recovery consists of inspecting known handles and resuming downloads. |
| `resolveOutput(handle, outputRef) → DownloadTicket` | Obtain a current trusted HTTPS download location and expiry when available. Provider authentication remains inside the adapter. Return no provider key to the downloader/browser. |

Preparation deserves its own operation because multipart uploads can take time and need durable association; hiding them behind the 120-second submission claim would incorrectly mark pre-submission work ambiguous. For initial Krea data-URI transport it may be local preparation. If multipart is selected, persist staged references keyed by connection and immutable source image so resuming preparation does not create a generation.

Persist staging expiry separately from immutable source identity and revalidate staged assets before claiming submission. Expired assets or input URLs require refreshed preparation, not a generation retry. For Krea, `attemptKey` is a local guard only; do not send an invented provider idempotency field. A future Comfy adapter also sends its supported header using the persisted attempt key.

`PipelineContract` uses the existing flat primitive form subset and semantic images. Mappings are Krea property names or explicit Comfy node IDs/input names, with declared final output nodes. Native schemas/graphs remain separate from the normalized form. There is no automatic JSON-to-JSON workflow conversion. Metadata absence or an unsupported schema blocks activation; it must not yield an empty runnable form.

The snapshot includes engine/API version, provider workspace/connection identity and credential source, pipeline configuration revision, native workflow/version or graph hash plus release/deployment/base URL, typed inputs and immutable media references, output mapping, and 4K target dimensions. Persist provider preparation separately. Credentials, signed URLs, and partner-node secrets are not immutable business inputs. Resolve secrets at dispatch, preserving access to the snapshotted workspace.

Handles contain provider ID and their original endpoint/connection. Output identity is stable within that handle: prefer provider asset ID plus output-node/slot where applicable; use a stable Krea output slot/manifest mapping and retain its original URL as provenance. Persist the manifest before downloads and upsert Pieces by local output ID. A renewed signed URL is a locator update, not a new Piece. Do not deduplicate distinct creative outputs solely because their bytes happen to match.

If Comfy is introduced, switching a pipeline to another release must not automatically stop or delete its older endpoint. Complete known jobs and private studio copies first, retain unresolved submission records for support, and verify job/asset access after stop/delete before establishing retirement timing. New submissions use the new binding; recovery continues against each original binding.

Keep capability metadata modest: `schema_mode`, `input_transports/limits`, `submission_deduplication` (`none_documented` or `reject_duplicate_24h`), `known_job_lookup`, `output_locator_kind`, and `reports_expiry`. Job cancellation can be recorded as provider support but need not be an interface method/UI action in this slice. Never turn a generic `supports_idempotency` flag into permission to replay a submission. Generation/edit/4K readiness belongs to each validated pipeline, not a blanket provider claim.

All tenancy checks, confirmation commands, history, parent/root lineage, curation, notifications, private storage, image validation, and ZIP exports remain domain responsibilities. Normalize provider errors to Spanish summaries; keep bounded, sanitized support detail separately.

## Exact changes before implementation planning

These are proposed edits to the current design, rather than a silent approval of a new engineering baseline. Only research checkpoint links are applied to the design/review in this session.

| Design location | Required revision |
| --- | --- |
| §§1–3, §4 diagram | Describe studio-configured pipelines with Krea as the recommended initial adapter. Replace hardwired `KreaClient` as the domain boundary with the five operations above. Keep Laravel/Filament, Spanish UI, standard layouts, and all settled product decisions. |
| §§4.1–4.3, §6.2 | Separate normalized form schema, provider source schema/graph, and input/output bindings. Krea still imports `input_openapi_schema`; null/unsupported schema is an actionable readiness failure. Comfy registration is deferred and requires a studio manifest, not a universal graph editor. |
| §4.4 preparation/submission | Complete image preparation before claiming `submitting`. Snapshot the provider and connection; maintain one durable local attempt and all returned jobs. Treat ambiguous POSTs and unknown provider responses conservatively. Never clear the claim to retry execution. |
| §4.4 recovery; §§6–7 | Retain the existing Spanish confirmation modal, final known-job check, linked replacement, and deduplication. Polling/retrieval never switches provider. Comfy duplicate-key rejection is not successful recovery. Provider expiry is distinct from local timeout; bounded recovery must account for it without promising 24-hour availability. |
| §4.4 results; §5 outputs/pieces | Move result parsing into the adapter. Krea uses only the declared image output structure; future Comfy selects final image outputs, not text/video or preview nodes. Replace URL-hash-only identity with stable provider output references and mutable download locators. For Krea, retain final images from completed child jobs even when siblings fail; `intermediate-complete` URLs are not established as final. For Comfy, retain committed images from configured final output nodes even if a later node fails. Mark the overall outcome accordingly. |
| §§4.1, 4.5 security | Keep private studio S3/MinIO storage and CloudFront delivery. For Comfy, resolve an asset to a fresh URL server-side, or validate its documented redirect explicitly. A generic no-redirect rule cannot be applied to its authenticated content endpoint. Never forward bearer headers to storage URLs; maintain provider-specific trusted hosts and bounded image decoding/downloads. |
| §§4.3–4.4 4K bindings | Add server-computed automatic target width/height or scale bindings, chosen by the Art Director for the actual workflow. A single fixed scale cannot meet the target for arbitrary source dimensions. Keep crop disabled and validate stored dimensions. No extra Editor controls, inherited 4K badges, or automatic downsampling of larger originals is introduced. |
| §§4.1, 4.5, 8 image limits | Validate per-image, aggregate request, pixel/decode, and provider input limits before submission. Three 20 MiB files expand to roughly 80 MiB in base64 before JSON overhead. Existing generated Pieces may also exceed upload limits when re-edited. Do not silently shrink originals or assume a 75 MB asset endpoint proves all workflows accept those images. |
| §5 provider names | Replace `pipelines.krea_version_id` with `engine` plus typed provider configuration; `generation_jobs.krea_job_id` with `provider_job_id` and native status/metadata; `pieces.krea_url` with provider provenance. Retain a distinct normalized status. Keep existing generation/output tables and lineage; no provider-specific tenancy or export tables. |
| §5 credentials, §§6.2, 8 | Resolve credentials by provider and existing brand/studio fallback. Pin source and workspace identity. Krea-only credentials may remain the initial concrete storage; defer Comfy credential controls until its adapter is selected. Do not build a general secrets-management subsystem. |
| §9, companion review | Incorporate all R2–R13 acceptance scenarios already drafted, plus multi-image payloads, multiple jobs/outputs, preparation interruption, nullable schemas, URL renewal, expired assets, and all exact-size aspect cases. Correct stale review statements that still describe first-job-only handling or missing export persistence as the current draft. Mark specification resolution separately from runtime verification. |
| §12 gates | Link this recommendation and both reports. List missing workflow/account artifacts and experiments below. Do not mark an implementation plan complete from documentation alone. Keep deployment/paid-operation approval separate from research. |

Campaigns still have **no statuses**. Shared marks still belong to everyone with campaign access; table checkboxes still select a temporary ZIP. Minimal Editor editing controls and the **3,840-pixel longest edge with preserved proportions** remain unchanged. Every generated final image is copied into **private studio-controlled storage**; provider retention is not the archive. Provider processing still entails sending image content to that provider and any configured partner model; private studio storage is not a zero-retention promise. See [Comfy retention](https://docs.comfy.org/support/data-retention) and the privacy findings in the companion reports.

## Evidence gates and proposed experiments — not authorized or run

### Gate A: identify the actual studio workflows, no generation spend

Obtain sanitized exports/metadata for the Santander, Skechers, Invierno, editor, and candidate upscaler versions: native schemas, output cardinality/mappings, hidden fixed values, model/LoRA references, representative approved outputs, and current account/workspace access. Obtain a newly issued server-side credential through the normal secret channel only when an authenticated experiment is authorized; never reuse the prototype key.

Also obtain the exact per-execution price or constituent-job price calculation and provider limits for these versions. Identify any provider-retention/third-party restrictions affecting the supplied brand images. If Comfy moves toward production, confirm the order form permits brand-client Editors to use the studio application: its standard access language refers to internal business use, so unrestricted downstream access should not be inferred. This is a provider question, not a conclusion that Media Ops is prohibited. [Comfy terms](https://comfy.org/terms-of-service). Expected generation cost: **$0** for document/export review. No credentials or account actions were used here.

### Gate B: Krea slice-1 smoke experiment

**Proposed scope:** the exact versions from Gate A; one generic text generation, one Skechers execution using reference/model/shoe images, one Invierno execution using its image/four text fields, two edits (an original and a 4K source), and three upscales of approved landscape, portrait, and square inputs: **8 execution submissions total**. Run the edit of a 4K source only after one of those upscales passes dimensional validation; otherwise halt that dependent case. This is eight workflow submissions, not a promise of eight provider jobs or images. Fix the inputs/configuration beforehand, capture sanitized responses and all output dimensions, and copy results into an isolated private studio test prefix.

Use those same jobs to observe worker/client restart, repeat safe status reads, interrupted download recovery, and late completion where it occurs. A separate local harness can retain a known job ID while the consumer loses it to test conservative unknown-submission handling; that does not prove provider discovery. Do not intentionally launch duplicate executions. Preflight schema and byte constraints first; no nonbillable Krea node-app validation endpoint was established. Designate the Skechers submission to exercise three approved near-limit files if Gate A confirms that configuration and its cost; otherwise leave large-input execution coverage explicitly unverified for a separately priced test. This smoke test checks contract viability; repeatability, odd-size rounding, and visual-quality approval require the broader matrix in the workflow-fit report.

**Expected spend:** not yet numerically verifiable for unpublished node-app contents. Calculate `C = C_text + C_Skechers + C_Invierno + C_edit_original + C_edit_4K + C_up_landscape + C_up_portrait + C_up_square`, including all billable children. Proposed spending ceiling: **US$10 for the eight submissions**, only if Gate A establishes they fit. If not, return the actual quote before running. A new Krea balance top-up has a documented **$5 minimum** and is funding, not measured consumption. [Krea API billing](https://www.krea.ai/docs/developers/api-keys-and-billing). No top-up is proposed automatically.

### Gate C: optional Comfy transport probe, then a separately scoped visual port

Only needed if the studio wants to validate Comfy now or a Krea gate fails. Proposed first graph, **`media-ops-transport-4k-probe-v1`**, uses core `LoadImage → ImageScale → SaveImage`, with Lanczos resize, crop disabled, and explicit computed width/height. Use studio-owned non-sensitive landscape, portrait, and square images. Pin ComfyUI and the built release; use no custom nodes, downloaded model weights, or partner calls. This measures asset transport, exact resizing, job/output recovery and queue behavior. AI enhancement quality, generator/editor equivalence, and sustained concurrency require separate experiments. [ImageScale documentation](https://docs.comfy.org/built-in-nodes/ImageScale).

Propose **5 new jobs**: three aspect cases, then two simultaneous repeats to check isolation. Poll and re-fetch those same outputs after client restart and signed URL expiry, within observed asset retention. One additional submission of an already accepted key, on the same deployment/connection and within 24 hours, tests the documented duplicate rejection; count it in the authorization scope as a possible sixth charge if the hosted behavior violates its documentation, then halt. Do not treat the replay as a production recovery policy. Use one temporary deployment with minimum 0/maximum 1; two requests may queue rather than run simultaneously. One release build only; any rebuild requires a revised proposal.

**Conditional cost estimate:** if RTX PRO 6000 is available and total billed worker time stays within 30 minutes, GPU cost is at most **$1.745**. The documented 50 GB worker disk has a listed full-month equivalent of **$6.50**; actual short-test proration needs confirmation. No model storage is expected for this core-only probe, but verify the staged footprint. **Build-minute price, egress, minimum funding, and billing granularity remain unquoted**, so a defensible total expected price cannot yet be stated. Proposed ceiling after obtaining those rates: **US$10**, including build, possible sixth run, and cleanup charges. This is a proposed budget, not a quoted estimate or permission. Confirm rates, available GPU/region, graph manifest, and teardown/asset-recovery behavior before requesting execution approval. [Resource rates](https://comfy.org/pricing), [worker/storage billing](https://docs.comfy.org/development/serverless/overview), [build charge evidence](https://github.com/Comfy-Org/comfy-cli/blob/main/comfy_cli/skills/comfy-build/SKILL.md).

After copying and verifying test assets, retire only that disposable deployment and confirm storage billing ends; pausing alone is insufficient. Include this cleanup in the eventual experiment authorization. A later visual-port experiment must name the actual generator/editor/upscaler graphs, model hashes/licenses, approved input sets, repeat count, partner-call charges, and total budget before it can be authorized. The transport probe cannot satisfy that gate.

## Decisions still needed

1. **Accept Krea-first scope, or make Comfy ownership a slice-1 requirement.** My recommendation is Krea first, with Comfy deferred. There is no need to reopen layouts, campaign lifecycle, curation, Editor controls, storage, or recovery confirmation.
2. **Authorize a priced live experiment later.** First provide the Gate A workflow/account artifacts through suitable channels. The US$10 figures are proposed ceilings; missing node-app and build prices must be resolved before a concrete execution approval request. No experiment is required to accept the research recommendation itself.

Documentation research is sufficient to recommend the architecture, but actual workflow access, transport, 4K behavior, output fixtures, and price evidence prevent declaring engine integration ready or finalizing the engine-specific implementation plan. This research-only session therefore records the exact design amendments and those blockers instead of constructing the app or presenting an unverified plan as finished.
