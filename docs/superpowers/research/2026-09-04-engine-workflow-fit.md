# Media Ops — workflow fit and Krea baseline

**Retrieved/inspected:** 2026-09-04. **Scope:** official public documentation and supplied prototype source. No credentials used, authenticated requests, prototype JavaScript execution, paid generations, or deployment. Embedded credential assignments were redacted before inspection output. The full canvas's embedded document was decoded as a JSON string, not executed.

**Evidence labels:** **Verified** means documented by the linked primary source or present in inspected local source; it does not mean runtime-tested. **Inferred** means an engineering conclusion from that evidence. **Unverified** means an account asset or experiment is still needed. **Unsupported** means available evidence does not justify the claim.

## 1. Findings that affect the engine decision

**Inferred:** Krea has the shortest documented path to preserving the existing integrations: four prototype operations already address Krea node-app versions. Their actual availability, graphs, models, quality, and output cardinality remain unverified. The product behavior can be reimplemented over Comfy, but calling two systems “node based” establishes no graph or model equivalence. A Comfy implementation requires separately authored workflows and art-direction acceptance.

**Unverified:** Neither supplied prototype implements the agreed 4K upscaler. Both engines need a tested sizing workflow before delivery can be accepted. Krea's public enhancer parameters offer candidates, not a proven 3,840-pixel contract.

**Verified:** Current Krea bearer API billing uses a separate USD workspace balance. Web-app compute units are a different meter. The API marketing page contains contradictory compute-unit wording; the dedicated billing documentation and usage reference explicitly agree on USD API billing. Do not use web subscription allowances to estimate this application's generation budget. [API billing](https://www.krea.ai/docs/developers/api-keys-and-billing), [API product page](https://www.krea.ai/features/api), [Usage API](https://www.krea.ai/docs/api-reference/usage/list-workspace-usage).

## 2. Krea integration baseline

| Area | Documented contract and practical limit |
| --- | --- |
| Discovery and versions | **Verified:** `GET /node-apps/{id}` takes a **version ID**, while its response distinguishes app `id`, `node_app_version_id`, version number/date, workspace, and visibility scope. Input/output schemas are nullable OpenAPI 3.1 JSON Schema objects. **Inferred:** retain both provider identifiers and both schemas; null is a readiness issue, not an empty form. [Get version](https://www.krea.ai/docs/api-reference/node-apps/get-a-node-app-by-version-id). |
| Version selection | **Verified:** `GET /node-apps/{node_app_id}/versions` lists runnable versions visible to the authenticated identity, with cursor pagination. **Unverified:** immutable underlying model revision, indefinite version availability, and historical reproducibility are not guaranteed by these fields. Pinning a node-app version does not prove pinned model weights. [List versions](https://www.krea.ai/docs/api-reference/node-apps/list-runnable-node-app-versions). |
| Submission | **Verified:** `POST /node-apps/{version_id}/execute` accepts schema-shaped JSON and bearer authentication. Its example returns an **array of jobs**, although prose calls the result singular. Status errors include 400/401/402/403/404/429. **Inferred:** preserve every returned handle; normalize a single object only as a compatibility behavior. No actual prototype-version response was obtained. [Execute](https://www.krea.ai/docs/api-reference/node-apps/execute-a-node-app). |
| Status | **Verified:** pending states include `backlogged`, `queued`, `scheduled`, `processing`, `sampling`, and `intermediate-complete`; terminal states are `completed`, `failed`, `cancelled`. An intermediate result is not final completion. Docs recommend polling every 2–5 seconds with backoff; provider timeout descriptions distinguish hosted tools (3 minutes) from external providers (2 hours). [Lifecycle](https://www.krea.ai/docs/developers/job-lifecycle). |
| Known-job recovery | **Verified:** `GET /jobs/{job_id}` returns current state and result/error information. **Inferred:** restarting a local worker can resume polling/downloads with persisted IDs and accessible credentials. This does not guarantee provider retention forever. [Get job](https://www.krea.ai/docs/api-reference/general/get-a-job-by-id). |
| Unknown submission | **Verified:** `GET /jobs` supports pagination and type/status filters; the documented contract has no client request ID or input-fingerprint filter. No execution idempotency key or guaranteed correlation mechanism was found. **Unsupported:** identifying an ambiguous submission by timestamp alone, or promising exactly-once execution. [List jobs](https://www.krea.ai/docs/api-reference/general/list-jobs), [Execute](https://www.krea.ai/docs/api-reference/node-apps/execute-a-node-app). |
| Cancellation/webhooks | **Verified:** lifecycle docs describe cancellation through `DELETE /jobs/{id}` only while queued/processing. Webhook docs describe terminal POSTs and receiver deduplication but no signing protocol; they do not establish a safe replacement for polling here. Preserve the settled polling approach. [Lifecycle](https://www.krea.ai/docs/developers/job-lifecycle), [Webhooks](https://www.krea.ai/docs/developers/webhooks). |
| Concurrency | **Verified:** tier-dependent concurrency, backlog, and request allowances are described only qualitatively. **Unverified:** numeric studio limits and latency under contention. Backlog behavior is not permission for automatic submission retries. [Rate limits](https://www.krea.ai/docs/developers/rate-limits). |

**Verified — credentials:** API access must be enabled for the workspace; owners/admins create tokens. The API acts as its own workspace identity, so web-app styles require workspace sharing before API use. **Inferred:** a brand key and studio fallback may see different assets; record the resolved credential source/workspace without recording its secret, and verify access to each configured version. Successful token creation alone does not establish workflow access. [API keys and billing](https://www.krea.ai/docs/developers/api-keys-and-billing).

**Verified — pricing baseline:** published example prices include Flux $0.04/image, Nano Banana Pro $0.15/image, and Topaz $0.10/upscaled image; actual model prices depend on request parameters. These are reference points, not prices for the supplied multi-node apps. Failed/cancelled jobs are documented as unbilled; completed jobs consume API balance, and exhausted balance rejects new requests with 402. **Unverified:** aggregate charges for a partially successful node app and the number of billable operations per supplied workflow. No cost/latency measurements exist. [API prices](https://www.krea.ai/features/api), [Billing](https://www.krea.ai/docs/developers/api-keys-and-billing).

**Verified:** `/usage` is an Enterprise workspace-service-key endpoint for compute-metered completed jobs and explicitly excludes direct API jobs. It cannot reconcile Media Ops USD API spending. Billing docs provide no public balance-read endpoint. [Usage](https://www.krea.ai/docs/api-reference/usage/list-workspace-usage), [Billing](https://www.krea.ai/docs/developers/api-keys-and-billing).

## 3. Images, outputs, and the exact 4K boundary

**Verified:** Krea's image-to-image guide accepts a remotely readable URL or a base64 data URI. Asset upload is a separate `POST /assets` multipart endpoint with a documented 75 MB file maximum, returning an asset ID, `image_url`, and nullable dimensions/size/MIME metadata. **Unverified:** each supplied node-app field's accepted transport and total execute-body limit. The asset-upload limit does not establish the execute JSON limit. [Image transport](https://www.krea.ai/docs/developers/examples/image-to-image), [Asset upload](https://www.krea.ai/docs/api-reference/assets/upload-an-asset).

**Verified documentation conflict:** both Krea Enhance and Topaz describe data-URI input but specify a 1,024-character maximum for `image_url`. That cannot accommodate normal full-sized image base64. **Inferred:** do not hard-code universal base64 transport from the prototype. Verify real schemas/provider behavior; candidate alternatives are server-created asset URLs or scoped studio signed URLs that remain valid through queueing and image retrieval. A URL is a bearer capability even when the bucket remains private. Provider asset privacy, expiration, and deletion behavior need confirmation. [Krea Enhance](https://www.krea.ai/docs/api-reference/image-enhance/krea-enhance), [Topaz](https://www.krea.ai/docs/api-reference/image-enhance/topaz).

**Calculated:** one 20 MiB upload becomes approximately 26.67 MiB of base64 before JSON overhead; three maximum-sized Skechers images produce approximately 80 MiB. Passing the local upload check therefore cannot establish provider transport readiness. Bound aggregate bytes and memory, and validate the chosen transport against all three inputs together. Preserve the source objects; silently recompressing reference images could alter art direction.

**Verified:** the generic job contract exposes `result.urls`, while node-app metadata also exposes a workflow-specific output schema. **Inferred:** snapshot the output schema/mapping and fixture-test how named workflow outputs relate to job results. Persist every final output manifest before fetching bytes; classify supported images explicitly. The prototype's recursive collection of arbitrary URL-looking strings is insufficient evidence that all such strings are final images. Copy every generated image into private studio storage, validate decoded MIME/dimensions, and retry failed downloads without generating again. [Job result](https://www.krea.ai/docs/api-reference/general/get-a-job-by-id), [Node-app schemas](https://www.krea.ai/docs/api-reference/node-apps/get-a-node-app-by-version-id).

**Unverified:** no general output-URL retention duration, refresh guarantee, or complete output-host allowlist was established. Krea's documented zero-data-retention option currently requires Enterprise enablement and names only Krea 2 Medium/Large/Medium Turbo; it cannot be assumed for these unknown node graphs. Commercial-use/privacy guarantees for particular models are outside the evidence obtained. [Zero data retention](https://www.krea.ai/docs/developers/zdr).

The settled delivery test remains `s = 3840 / max(W,H)` and stored dimensions `round(W*s) × round(H*s)`, without cropping/stretching. Landscape 16:9 is 3840×2160; portrait is 2160×3840; square is 3840×3840. Odd source dimensions must exercise rounding. An edit does not inherit its parent's 4K badge. Invalid delivery output remains downloadable but fails delivery acceptance. Already conforming pieces need no new execution; larger originals remain downloadable, with automatic downsampling deferred. [Approved design §4.4](../specs/2026-09-04-muse-media-ops-slice-1-design.md).

**Verified:** Krea Enhance exposes a numeric scaling factor; Topaz exposes width/height, model selection, `crop_to_fill`, and scaling/activation controls. **Inferred:** a workflow can potentially compute the scale or accept calculated target dimensions. **Unverified:** parameter precedence, exact rounding, aspect fidelity, and whether these controls are exposed by a runnable node-app version. A fixed “4×” setting cannot satisfy every source size. This requires either dynamic automatic dimension bindings or sizing logic inside the workflow, without adding Editor controls. A model's advertised “4K” label is not proof of the agreed exact dimensions. [Enhance parameters](https://www.krea.ai/docs/api-reference/image-enhance/krea-enhance), [Topaz parameters](https://www.krea.ai/docs/api-reference/image-enhance/topaz).

## 5. Portability and acceptance matrix

**Inferred:** forms, immutable input snapshots, brand authorization, generation history, image lineage, shared curation, Spanish Filament flows, private storage, and ZIP exports are provider-independent behavior. A Comfy workflow must explicitly bind those inputs to its own graph and map its outputs back. Recreating prompts, reference preprocessing, model/LoRA selection, seeds/sampling, branch ordering, and enhancement settings is separate creative/engineering work. Krea's node guide itself distinguishes model parameters and workflow connections and warns its model inventory changes; an API form schema reveals neither the whole graph nor its trained assets. [Krea Nodes](https://www.krea.ai/docs/user-guide/features/nodes).

The following are **proposed acceptance checks**, unperformed for both engines. Functional success and art-direction success are separate gates; equal seeds across different models do not establish visual equivalence.

| Case | Functional acceptance | Art-direction acceptance |
| --- | --- | --- |
| Scene generation | Exact configured text binding; expected image count/order verified against the real workflow; all outputs stored | Brand composition, palette, lighting, subject placement, and scene adherence against AD-approved examples |
| Skechers references | Three independently mapped, required images; changing one input is traceable in snapshot/history | Preserve intended model/pose and specific shoe identity, materials, proportions, logos; avoid reference-role swapping |
| Invierno composition | One image plus all four labelled texts; no field dropped or merged without explicit workflow design | Product matches source; each requested scene is represented as intended; seasonal treatment stays consistent |
| Edit | Current viewed version plus instruction only; parent/root lineage retained; all final images handled | Requested change is achieved while protected product, face, lighting, and layout details remain acceptable |
| 4K delivery | Landscape, portrait, square, odd sizes, conforming source, and larger source; exact stored dimensions and badge rule | No crop/stretch; acceptable detail and edges at 100%; no invented branding, texture, halos, or unintended face changes |
| Output handling | Multiple jobs/images, partial failure, empty/malformed result, unsupported output, one failed download | Reviewer can inspect surviving outputs; failed output does not silently disappear or get mistaken for approved quality |
| Recovery | Interrupt around submit persistence; resume known IDs; late completion and duplicate downloads; unknown submission stays explicit | No automatic cross-engine replacement changes a requested result |
| Transport/tenancy | Three 20 MiB inputs, expired URLs, private reads, invalid MIME, foreign-brand uploads; chosen transport proven | Reference preprocessing preserves approved source information |
| Repeatability/cost | Record exact version, model configuration, output count, elapsed time, actual charges, and acceptance rate over repeated matched inputs | Compare all samples blind against the same rubric; report acceptable pieces per cost, not selected highlights |

Recovery must precede a rerun. Another potentially billable execution needs the settled Editor confirmation modal, final check of known original jobs, linked replacement history, and confirmation deduplication. A secondary engine chosen per pipeline does not authorize automatic fallback. UI screenshot matching, quotas, campaign statuses, and curated libraries remain outside this slice.

## 6. Missing evidence before an engine quality claim

1. Workspace-authorized metadata and sanitized schemas for the four version IDs; confirmed visibility, API entitlement, and fresh server-held credential setup. Prototype credentials are not research credentials.
2. Actual Krea graphs or an AD-authored equivalent specification: models/revisions, prompts/fixed values, reference order/processing, LoRAs and access rights, branch/output meaning, seeds, and postprocessing.
3. A runnable upscaler definition with exact sizing behavior; any Comfy candidates with matching input roles, pinned deployment/environment/model assets, and explicit final-image outputs.
4. Approved reference/model/product images with known provenance, representative Santander/Invierno prompts, protected-detail edit instructions, and accepted/rejected output examples. Bundled images alone do not establish benchmark input/output provenance.
5. Sanitized submission, status, failure, multi-output, and completed fixtures; actual result hosts, retrieval expiration, transport ceilings, node-app billing behavior, and account rate/concurrency limits.
6. An explicitly authorized, budgeted comparison after these assets exist. No paid experiment is authorized by this report. Cost, latency, retention recovery, and visual parity remain unmeasured.
