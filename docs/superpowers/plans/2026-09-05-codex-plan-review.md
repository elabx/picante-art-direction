# Codex review of the slice 1 implementation plan

**Date:** 2026-09-05
**Reviewed:** `docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md` (commit e126492) against the converged spec.
**Status:** findings pending user decisions; plan not yet revised.

## 1. Spec requirements with no corresponding task in the plan

1. [HIGH] **Error redaction and structured logging are unassigned.** [Spec §7](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:180) requires contextual logs and provider errors “redacted then truncated to 2 KiB.” [Plan Task 7](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:837) directly appends `$detail`, and neither it nor Tasks 15–16 assigns sanitization, truncation, or the required logging context.

2. [HIGH] **Invalid pipelines are never automatically deactivated.** [Spec §4.2](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:78) requires an invalid active pipeline to be deactivated; §5 also requires clearing invalid defaults. [Plan Task 9](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1139) only saves `readiness_errors`, and Task 19’s field-save behavior only evaluates readiness and increments the revision. Task 10 supplies manual deactivation, but no task connects it to either invalidation path.

3. [HIGH] **The recovery controls are incomplete.** [Spec §4.4](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:102) requires manual “Comprobar estado” and recovery through retrying downloads; §6.1 requires restart from the drawer. [Plan Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1471) defines `checkStatus()` but no UI task invokes it, no service/action retries exhausted downloads, and Task 22’s JobsBell has no restart action.

4. [HIGH] **Fixed image inputs have no administration or retention workflow.** [Spec §5](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:133) requires `pipeline_inputs` to retain configured uploads. [Plan Task 14](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1343) assumes fixed images exist “via `pipeline_inputs`,” but Task 19 offers only a JSON/string `TextInput` for `fixed_value`. No task finalizes these admin uploads or maintains the pivot when fields change.

5. [HIGH] **Accepted work surviving campaign soft deletion is unassigned.** [Spec §4.5](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:121) requires deletion to block new commands while letting accepted work finish. [Plan Tasks 15–16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1395) do not specify a deleted-campaign command check or a worker lookup that can still resolve deleted campaigns and their brands. No test exercises this lifecycle.

6. [MEDIUM] **The immutable snapshot omits the supported schema.** [Spec §4.4, CreateGeneration](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:100) explicitly includes the “supported schema” in `execution_snapshot`. [Plan Task 15](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1395) enumerates `engine`, `provider_ref`, `pipeline_label`, `config_revision`, `credential_source`, `kind`, `inputs`, `labels`, `bindings`, and `source_piece`, with no schema entry or snapshot-immutability enforcement task.

7. [MEDIUM] **Production storage/queue configuration and the required storage integration checks are absent.** [Spec §§3, 4.5 and 9](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:115) require CloudFront origin access control, bucket/CloudFront CORS, production Redis, a real 12–20 MiB MinIO upload/preview/download, and staging expiry/renewal verification. [Plan Tasks 24–25](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1803) cover Krea fixtures and a general walkthrough, without these checks or production wiring; Tasks 2 and 12 only configure MinIO/disks and URL signing.

8. [MEDIUM] **Redirect endpoints do not implement the specified image renewal behavior.** [Spec §4.5](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:119) requires image components to refresh URLs before expiry or after failed loads. [Plan Task 20](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1663) supplies fresh redirects “on request,” but assigns no expiry timer, failed-load handler, or redirect-cache behavior that causes another request. Covers additionally use the signer directly, outside the two proposed media routes.

9. [MEDIUM] **Several explicitly required acceptance tests have no assigned cases.** [Spec §9](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:193) requires restart-modal cancellation, disabled Viewer upscale without a pipeline, and edit parent/root results. [Plan Task 22’s tests](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1745) cover edit existence, selection, foreign access, and seen marking, but none of those cases; Task 16 tests restart services without exercising cancellation.

10. [MEDIUM] **The admin field editor omits the required source information.** [Spec §6.2](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:167) requires read-only field name, source schema, and required status. [Plan Task 19](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1622) lists pipeline metadata and editable override columns, without assigning those read-only field displays. They are necessary for the Art Director to understand the overrides and readiness errors.

11. [LOW] **Brand-logo presentation is missing.** [Spec §§1 and 6.1](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:11) require the current brand’s logo where supported. [Plan Task 17](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1564) configures `brandName()` but no logo presentation; Task 18 only stores `logo_path`.

## 2. Tasks whose code or tests contradict the spec or contradict each other

1. [HIGH] **Upload authorization checks the brand instead of the owner.** [Spec §9](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:193) requires that an Editor cannot use “another user’s upload.” [Plan Task 13](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1302) defines `authorize(int $uploadId, Brand $brand)` using only `brand_id`, with no user parameter; Task 15 also omits ownership checks from its authorization list. Another Editor’s same-brand upload therefore satisfies the specified lookup.

2. [HIGH] **Image references cannot pass the specified shared validator.** [Plan Task 14](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1341) composes images as `['__upload' => id]` or `['__piece' => id]`, then “Validates every value with `PipelineReadiness::validateValue`.” [Task 10](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1207) requires “string/image → `is_string`.” These arrays fail that rule, contradicting Task 14’s successful edit test and the reference-based snapshots required by spec §4.4.

3. [HIGH] **The extra-key rejection test requires successful acceptance.** [Spec §4.3](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:94) says “Extra client keys are rejected.” [Plan Task 14’s test](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1358), named “composes visible, fixed, and bound inputs and rejects extra keys,” passes `['evil' => 'x']` and immediately expects a successful payload. Correct rejection would make that test fail.

4. [HIGH] **Unsupported schemas and supported constraints are not consistently enforced.** [Spec §4.2](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:74) rejects unrecognized keywords and supports string `pattern`. [Plan Task 9](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1085) declares `SUPPORTED_KEYS` but never uses it, checking only a finite denylist; Task 10’s prescribed value checks omit `pattern`. Moreover, readiness checks editable `input_type = unknown`, without requiring revalidation of unsupported `source_schema` after an admin changes that type.

5. [HIGH] **Sync silently changes incompatible configuration instead of blocking it.** [Spec §4.2](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:76) says “New required properties … or incompatible overrides block readiness until configured.” [Plan Task 9](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1130) creates new fields visible and replaces incompatible `input_type` automatically. Task 10 has no rule recording either condition as awaiting configuration, so a newly required visible generator field or replaced override can immediately be considered ready.

6. [HIGH] **The result-size check occurs after an unrestricted buffered download.** [Spec §§4.1 and 4.5](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:68) require a 64 MiB cap and no image bytes on local disk. [Plan Task 8](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:981) performs `get($url)`, reads `$res->body()`, and only then checks `strlen($bytes)`. This does not cap transfer/buffering, and Guzzle’s default body streams spill to disk above 2 MB. [Guzzle documentation](https://docs.guzzlephp.org/en/stable/psr7.html#body)

7. [HIGH] **Image validation does not decode the image, and invalid images get the wrong failure category.** [Spec §4.1](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:68) requires bytes “decoded and validated,” while [Plan Task 8](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:967) only calls `getimagesizefromstring()` and checks its reported MIME. PHP explicitly cautions that the equivalent `getimagesize()` operation is not image-validity verification. Task 16 also funnels downloader failures into `download_failed`, whereas spec §7 requires non-image output to produce `invalid_result`. [PHP documentation](https://www.php.net/manual/en/function.getimagesizefromstring.php), [validation warning](https://www.php.net/manual/en/function.getimagesize.php)

8. [MEDIUM] **`SchemaSubset::classify` has mismatched signatures and a failing expected count.** [Plan Task 9’s interface](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1001) declares `classify(array $propertySchema)`, but its implementation requires `classify(array $schema, string $name)`. The test at line 1025 expects one error for `type => array` plus `items`, while lines 1092 and 1096 generate both `"Tipo no soportado: items"` and `"Tipo no soportado: array"`; deduplicating those distinct strings still leaves two.

9. [MEDIUM] **Polling fixtures omit the snapshot keys required by the dispatch contract.** [Plan Task 15](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1395) requires `credential_source` and `provider_ref` in the snapshot, consistent with spec §§4.1/4.4. [Task 16’s happy-path fixture](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1480) supplies only `['inputs' => []]`; other polling fixtures inherit Task 5’s empty snapshot. These fixtures cannot establish correct polling through the required pinned credential source and need a consistent snapshot fixture.

10. [MEDIUM] **The test labelled concurrent performs sequential activation.** [Spec §9](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:193) requires editor/upscaler/default invariants “under concurrency (real MySQL).” [Plan Task 10](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1189) names its test “even under concurrent activation” but calls `activate($a)` and only afterward `activate($b)` on the same execution path. That proves sequential validation, not locking under competing transactions.

11. [MEDIUM] **Blanking a brand key cannot perform the advertised fallback change.** [Plan Task 18](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1595) tells the user “Déjala vacía para usar la clave del estudio,” but specifies `->dehydrated(fn ($state) => filled($state))` and initializes edit state to `null`. For an existing brand key, submitting blank omits the attribute and preserves that key, so the promised switch to the studio fallback never happens.

12. [MEDIUM] **Required nullable fields have contradictory form rules.** [Spec §4.3](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:94) says “Required visible fields get `required()`.” [Plan Task 11](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1217) instead specifies `required` only when `required && !nullable`, while Task 14 still requires missing required values to throw. Form and composer therefore disagree about required nullable fields.

13. [LOW] **The default prompt-selection rule differs from the spec.** [Spec §4.2](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:77) selects “the first non-image string.” [Plan Task 9](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1002) says “the first required non-image string,” but its actual query also inherits the `fields()` relation’s existing `sort_order` ordering before adding `orderByDesc('required')`. The interface, query ordering, and spec should name one consistent selection rule.

## 3. Laravel 12 / Filament 5 / Livewire 4 API usages that are wrong, deprecated, or unverified

1. [HIGH] **`PendingRequest::retry(..., throw: false)` still throws connection exceptions.** [Plan Task 7](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:868) does not wrap those exceptions in `KreaException`, although Task 9 promises that exception type and Task 19 only deletes a newly created pipeline on `KreaException`. A network failure therefore bypasses the specified cleanup/error path required by spec §6.2. Laravel 12 explicitly documents this behavior. [Laravel HTTP retries](https://laravel.com/framework/docs/12.x/http-client#retries)

2. [HIGH] **Framework-dependent “Unit” tests lack Laravel bootstrap.** [Plan Task 7](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:918) binds `Tests\TestCase` and `RefreshDatabase` only to `'Feature'`. Tasks 7, 8, 11, and 12 nevertheless place tests using `Http::fake()`, `config()`, `base_path()`, database factories, and container bindings under `tests/Unit/`. Laravel 12’s default unit tests do not boot the application, so those prescribed tests cannot run as written. [Laravel testing documentation](https://laravel.com/framework/docs/12.x/testing#introduction)

3. [HIGH] **`FileUpload::preventFilePathTampering()` is incomplete for the custom generator form.** [Plan Task 11](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1219) enables it without the ownership callback explicitly required by spec §4.5. Filament 5 rejects submitted string paths without a matching record attribute unless `allowFilePathUsing` approves them; Task 21 instead expects retained inputs to remain reusable after finalization replaces paths with upload IDs. The plan needs an explicit authorized mapping between FileUpload state and finalized records. [Filament 5 file-upload documentation](https://filamentphp.com/docs/5.x/forms/file-upload#preventing-file-path-tampering)

4. [MEDIUM] **Laravel’s `boolean` rule rejects the proposed JSON-encoded boolean enum keys.** [Plan Task 11](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1217) combines primitive validation rules with Select keys generated by `json_encode($value)`; Task 21 validates before Task 14 decodes those keys. Laravel 12’s `validateBoolean()` accepts booleans, `0`/`1`, and `"0"`/`"1"`, but not `"true"`/`"false"`. Thus valid boolean-enum selections fail before the type-preserving composition required by spec §4.3. [Laravel 12 validator source](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Validation/Concerns/ValidatesAttributes.php)

5. [MEDIUM] **`Eloquent\Builder::value()` decrypts the attribute used in the encryption test.** [Plan Task 4](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:405) expects `Brand::query()->…->value('krea_api_key')` not to equal `'secret-key'`, while the same task installs an encrypted cast. Laravel 12’s `value()` retrieves the model attribute through its casts, so the correct implementation returns the plaintext and fails this assertion. Task 18’s `DB::table('brands')->value(...)` correctly checks stored ciphertext. [Laravel 12 Eloquent source](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Database/Eloquent/Builder.php)

6. [MEDIUM] **The connection-failure fake bypasses the request recorder.** [Plan Task 7](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:815) uses `Http::fake(fn () => throw new ConnectionException(...))`, then expects `Http::assertSentCount(1)`. That direct throw bypasses the response recorder and Laravel’s Guzzle-connection-exception recording path; it does not establish one recorded request. Use the documented `Http::failedConnection()` path or explicitly count callback invocations. [Laravel 12 HTTP client source](https://github.com/laravel/framework/blob/12.x/src/Illuminate/Http/Client/PendingRequest.php), [faking exceptions](https://laravel.com/framework/docs/12.x/http-client#faking-exceptions)

7. [MEDIUM] **`wire:poll.5s.visible` checks viewport visibility, not tab visibility.** [Plan Task 22](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1740) uses it for the spec §6.1 requirement to poll while the tab is visible. Livewire 4’s `.visible` modifier gates polling on the element being in the viewport; background tabs are separately throttled, rather than completely stopped. This is not an exact implementation of the specified visibility condition. [Livewire 4 polling documentation](https://livewire.laravel.com/docs/4.x/wire-poll)

8. [LOW] **`Filament\Forms\Components\Placeholder` is deprecated in Filament 5.** [Plan Tasks 21 and 23](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1687) prescribe `Placeholder` for configuration messages and settings placeholders. Filament 5 retains the class but marks it deprecated in favor of `Filament\Infolists\Components\TextEntry` with `state()`. [Filament 5 source](https://github.com/filamentphp/filament/blob/5.x/packages/forms/src/Components/Placeholder.php)

## 4. Ordering problems between tasks

1. [HIGH] **Evidence gates occur after the implementation they are meant to gate.** [Spec §12](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:209) calls them gates “before implementation” and explicitly forbids marking KreaEngine tasks done without Gate B fixtures. [Plan Task 7](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:920) reaches PASS/commit using invented fixtures, whereas schemas, real transport evidence, and size bindings arrive only in Task 24. The initial prerequisites request IDs, but do not supply the missing schema/output evidence.

2. [HIGH] **Task 15’s passing submission test requires Task 16’s job class.** [Plan Task 15](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1436) runs `RunGenerationJob::handle()` and asserts two dispatched `PollGenerationJob` instances. [Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1465) is the task that creates `PollGenerationJob.php`. Task 15 cannot complete its stated successful submission path in the declared sequence.

3. [HIGH] **Earlier UI verification renders later-task dependencies.** [Plan Task 17](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1567) installs an unconditional `@livewire('jobs-bell')` render hook and immediately tests authenticated app pages, but JobsBell is created in Task 22. Task 20’s populated campaign table also calls `Generator::getUrl()` before Task 21 creates Generator. These dependencies need earlier shells or later verification milestones.

4. [LOW] **Task 9 explicitly requires an exception to the declared sequence.** [Plan Task 9](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1118) constructor-injects `PipelineReadiness`, which Task 10 creates. Its Step 4 acknowledges this and suggests implementing Task 10 first or stubbing `evaluate()` to return `[]`. The dependency is therefore recognized, but the stub alternative makes a Task 9 PASS insufficient evidence for the readiness behavior required by spec §4.2.

## 5. Risks in the queue/claim/recovery design

1. [HIGH] **Output-manifest identity is unstable under poll replay and concurrent children.** [Plan Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1468) assigns each completed child outputs whose `index` “continues from the max existing index of the generation.” Replaying the same completed child while siblings remain active allocates new indices for the same results; competing children can also choose the same next index unless allocation is serialized. [Spec §5](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:136) and Task 5 only make `(generation_id,index)` unique, so neither defines a stable child/output identity that makes manifest replay safe.

2. [HIGH] **Worker death can leave a generation permanently `submitting`.** [Spec §4.4](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:101) and [Plan Task 15](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1397) correctly prevent another submit once the claim succeeds. Neither defines a stale-claim transition or recovery path if the process dies during expansion, during submission, or after acceptance but before saving provider IDs. With `$tries = 1`, later delivery cannot repair this state, and restart visibility depends on failure states that were never written.

3. [HIGH] **Persistence and queue dispatch have unrecovered crash windows.** [Plan Task 15](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1395) uses `DB::afterCommit` for the initial dispatch; Tasks 15–16 subsequently persist provider jobs/manifests and dispatch follow-up jobs. No task durably records and repairs a dispatch that fails after its database state commits. A generation can consequently remain `pending`, `submitted`, or `downloading` without queued work; the deferred reconciler in [spec §10](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:199) does not cover this slice.

4. [HIGH] **Inspect failures bypass the ten-minute timeout indefinitely.** [Plan Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1468) catches every `KreaException`/`ConnectionException`, increments `poll_failures`, redispatches, and returns before checking elapsed time. Persistent connection failure—or a permanent 401/404—therefore repeats every 60 seconds without reaching the timeout required by [spec §4.4](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:102). The delay is capped, but the retry duration and error classification are not.

5. [HIGH] **A partial late recovery can disable polling of remaining children.** [Plan Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1468) permits polling a terminal generation only when its reason is `poll_timeout`. Suppose one recovered child creates outputs, another remains pending and re-times out the generation, and the first child then exhausts a download: `settle()` returns while the other child is non-terminal, leaving the generation-level timeout/processing interactions unresolved. More generally, polling eligibility depends on mutable aggregate failure state rather than each child’s recoverability, despite [spec §4.4](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:102) requiring remaining children and late results to remain recoverable.

6. [HIGH] **Download replay is an overwrite, not a no-op.** [Spec §4.4](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:103) says Piece creation is keyed by `generation_output_id` and “replays are no-ops.” [Plan Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1469) always downloads, writes the object, and uses `updateOrCreate`, without a stored-output early return or per-output claim. Duplicate jobs can overwrite an already delivered asset, compete on attempt counts, or record failure after another execution successfully stored it.

7. [HIGH] **Restart eligibility and source authorization are incomplete.** [Spec §4.4](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:111) requires known-job recovery and renewed membership/source-access authorization. [Plan Task 16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1471) checks membership and active pipeline, but specifies no source-upload/parent reauthorization or explicit rejection of ineligible original statuses. It only inspects known jobs for `poll_timeout`, and only suppresses replacement when **all** completed, leaving partial completed results outside the specified recovery branch; checking pipeline activation before recovery can also block retrieval of accepted work after configuration changes.

8. [HIGH] **Edit/upscale actions lack the stable request identity used for series.** [Plan Task 21](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1688) explicitly retains a mounted `requestId` until successful submission. [Task 22](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1733) instead describes edit/upscale calls using `uuid`, with no equivalent retained client ID. Generating a UUID per action invocation would turn duplicate delivery into distinct Generations and potentially distinct paid executions, contrary to spec §4.4’s idempotent form-submit requirement.

9. [HIGH] **Worker and HTTP timeout budgets conflict.** [Plan Tasks 15–16](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1397) set submit/poll job timeouts to 90 seconds but never adjust queue `retry_after`; Laravel 12’s database/Redis defaults are also 90 seconds. DownloadOutputJob has no timeout override, while Task 8 permits a 60-second HTTP download and Task 25 runs the worker with its default 60-second timeout, leaving no allowance for inspection/storage. Laravel requires the worker timeout to be shorter than `retry_after`; these budgets increase duplicate-processing and stuck-output risks. [Laravel defaults](https://github.com/laravel/laravel/blob/12.x/config/queue.php), [queue timeout documentation](https://laravel.com/framework/docs/12.x/queues#job-expirations-and-timeouts)

10. [HIGH] **Input cleanup can delete an object just as it becomes referenced.** [Plan Task 25](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1819) selects uploads with no reference rows and removes the object first. Task 15 can concurrently attach `generation_inputs`, with no shared lock or deletion-claim protocol specified. The database deletion may then fail on the new reference after the object is already gone, violating retained-upload guarantees in [spec §4.5](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:121).

11. [MEDIUM] **The schema lock does not prevent a lost revision increment.** [Plan Task 9](docs/superpowers/plans/2026-09-05-muse-media-ops-slice-1.md:1125) executes `$pipeline->lockForUpdate()->find($pipeline->id)` but discards the returned fresh model, then saves `$pipeline->config_revision + 1` from the original instance. Two syncs that loaded the same revision can serialize under the lock yet both save the same next revision. A form created between them can pass Task 15’s revision check against changed configuration, weakening the stale-submission guarantee in [spec §4.3](docs/superpowers/specs/2026-09-04-muse-media-ops-slice-1-design.md:94).

12.
